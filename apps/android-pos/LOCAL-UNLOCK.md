# Native local staff unlock and clock source

Candidate native security components, now connected to the preparation coordinator and native PIN dialog. Sale issuance remains disabled; these components do not establish production readiness.

`NativeStaffUnlock(Context, NativeJournal, NativeClockSource)` implements the checkout engine's native `UnlockGuard`. Construction and PIN methods are package-private. The host calls `isProvisioned(binding)`, `provisionVerifiedStaff(binding, char[])`, `unlock(binding, char[])`, `lock()` and `requireUnlocked(binding)`. Provisioning requires a fresh, independently verified native online staff/device identity and native PIN confirmation. An existing verifier is never replaced by provisioning. PIN reset/recovery requires a separately reviewed online workflow; this implementation intentionally supplies no reset, clear or deletion method.

PINs are 8–12 ASCII digits. Each credential has a 32-byte random salt, platform PBKDF2-HMAC-SHA256 with 600,000 iterations and a 32-byte output, followed by a device Keystore HMAC-SHA256 pepper. The pepper never exports into the application. The authenticated private SQLite records retain the verifier and throttling state, never the PIN or a server password. PIN `char[]` inputs are consumed and cleared; temporary derived byte arrays and PBEKeySpec passwords are also cleared. The host must clear its native input control and must run expensive KDF operations on its native worker.

Local PIN support deliberately fails with `pin_kdf_unsupported` on API24/25 or when the platform PBKDF2-SHA256 provider is unavailable. The official [SecretKeyFactory algorithm table](https://developer.android.com/reference/javax/crypto/SecretKeyFactory) lists PBKDF2-HMAC-SHA256 from API26. No custom KDF, SHA1 downgrade or software substitute for a lost Keystore key is used.

Every PIN attempt is charged and committed before the expensive verification step. A process death during verification therefore consumes an attempt. Five failures impose a 15-minute lockout. The lockout uses native elapsed time; wall-clock changes cannot expire it. A reboot restarts the full lockout interval on the new boot. After ten failed attempts the credential requires explicit online recovery. The failure counter resets only after a successful PIN verification; waiting or restarting never resets it. A successful tenth submission can still succeed if the preceding nine submissions failed. The verifier remains immutable. Each successful unlock creates only a five-minute in-memory session, bound to the full organization/branch/device/actor/epoch/fingerprint/shift binding. A new process or boot requires another unlock. Concurrent credential changes invalidate an older memory session through its authenticated record revision.

`NativeClockSource(Context, NativeJournal)` implements `ClockSource`. It reads [Settings.Global.BOOT_COUNT](https://developer.android.com/reference/android/provider/Settings.Global#BOOT_COUNT), [SystemClock.elapsedRealtime](https://developer.android.com/reference/android/os/SystemClock#elapsedRealtime()) and `System.currentTimeMillis()` natively. Its boot UUID is deterministically derived from the installation UUID and OS boot count, so a process restart cannot create a fresh boot identity. Authenticated SQLite high-water state survives restart. A missing boot signal, backwards boot counter, backwards elapsed time within the same boot, or backwards wall time latches a failure. Forward wall time does not advance PIN cooldown. Checkout additionally applies its separately persisted `OfflineClock` drift and authority-expiry rules.

The current financial clock policy rejects even a small backwards wall-clock correction, matching `OfflineClock`. This is conservative and may require an online recovery workflow after a legitimate clock correction. No silent re-anchoring/reset API exists. A missing private database with its surviving Keystore key, or a missing key with surviving private records, fails closed. New security stores are not initialized over existing ledger custody without a reviewed migration.

These are managed-device application protections, not a claim of tamper-proof physical time or a hardware monotonic failure counter. Keystore hardware backing is not asserted. A compromised application/OS can potentially invoke its keys; restoration of a complete authenticated old filesystem snapshot is outside the protection offered by SQLite plus HMAC. Android backup/device-transfer is disabled for this application. The [Android Keystore security model](https://developer.android.com/privacy-and-security/keystore) explains key extraction protection and its process-compromise limits.

Verification is split: `NativeStaffSecurityTest` uses unique synthetic private databases and Keystore aliases, tests real Android cryptographic operations, injects native clock observations for rollback/lockout cases, and separately reads actual OS boot/elapsed signals. It verifies cleanup of each fixture. Injection constructors remain package-private and are never callable from JavaScript. Emulator results, physical-device acceptance and final host/UI integration are reported separately; the existence of these tests does not establish that they passed.
