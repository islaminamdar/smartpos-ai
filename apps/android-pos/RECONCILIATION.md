# Native receipt and allocation recovery

Candidate only. These methods do not enable new sales, close a cash shift, activate subscriptions, or establish production readiness. SQL017, server signing configuration, and the complete native sale/reconnect acceptance are still release gates.

`getReconciliationState()` reads local counts only. `reconcileOffline()` explicitly uploads up to 100 pending receipts in their original local order, stopping on the first failed or rejected receipt. It then uploads already-saved terminal allocation declarations only when the entire receipt outbox is empty. Another explicit call continues a larger batch. It never starts payment, creates a receipt, signs a new terminal declaration, or automatically retries a charge.

Historical upload uses only the two fixed HTTPS import/seal paths. No login cookie is sent or adopted, and no current login, PIN unlock or unexpired selling permission is required. The app retains its original device identity and ledger after sign-out. Lost/corrupt keys or custody remain errors; reinstalling or clearing app data is not recovery.

A receipt leaves the outbox only after its exact original document matches the response and a pinned server signature confirms the current upload's receipt ID, payload hash, authority, epoch and sequence. A valid acknowledgement for another receipt is rejected. Network errors, malformed replies and reconciliation exceptions retain the original receipt and outbox entry. Exceptions are stored immutably and remain visible until that receipt receives a valid signed acknowledgement; operator resolution on the server is separate work.

`finishOfflineAuthority({authorityId})` operates only on the current prepared allocation for the same signed-in staff member. The screen binds explicit confirmation to the actor, allocation and invoice range, then opens a native PIN dialog. The native owner checks the exact allocation and PIN before persisting its original device-signed terminal declaration. Uncertain payment intents block finishing. Only after this durable step does it attempt upload. Cancellation does not finish anything; a lost upload response keeps the original declaration for exact retry. It does not close the shift or request a replacement allocation.

A seal confirmation is an operational HTTPS response, not a signed receipt custody acknowledgement. It must match the saved declaration's authority, final sequence and hash. SQLite schema 3 adds immutable seal confirmations and upload exceptions without replacing any prior receipt, intent, key, clock, chain or bundle. The verified schema 2 migration preserves those records.

If preparation first receives an already-expired allocation, the native engine verifies its signed fresh handoff, retains the never-installed bundle and atomically seals it using the existing device chain head. Its clock anchor is outside that allocation's validity and the terminal seal prevents issuance. No invoice number is reused. Existing installed bundles are never reset by this retention method. A previously active allocation that expires requires the separate explicit finish action.

An expired first enrollment proof can be renewed only after the exact enrollment endpoint returns a validated request-bound definitive pre-insert rejection. The native owner persists that outcome. The next explicit preparation attempt obtains a new signed time context and signs a new proof while preserving the request ID, key and scope. Timeouts, generic errors and lost replies reuse the original request. A previously committed enrollment remains an exact replay, even after its proof has aged.

Verification uses real Android Keystore/SQLite with synthetic keys, profiles and HTTPS responses. Native PIN dialog tests inspect actual masked controls, secure-window flags, cancellation and background wiping without submitting credentials or financial actions. Browser fixtures test only presentation and interaction. These checks do not replace live two-device restart/reconnect, printer or supervised manager acceptance.

Candidate missing-bundle recovery, financial screens, signed manager return/void outcomes and controlled allocation continuation now exist. See [NEXT-ALLOCATION.md](NEXT-ALLOCATION.md). Native drawer close and complete next-shift operation, controlled PIN/clock/staff/device-loss recovery, broader exception tools and full operational release acceptance remain pending. SQL017–022 are not applied live.
