# Staff access UI

- `StaffManager({actorId, branchId, deviceId, disabled, onChanged?})` uses the shared staff schemas and scoped staff/invitation APIs. Managers have fixed cashier/current-branch controls; owners can manage cashier/manager roles and supported branch scope. Owner rows are read-only. The server remains the authority for every permission and open-shift check.
- `StaffInvitation()` is the `/staff/accept` page body. It immediately removes the application invitation fragment from the URL, keeps that token in memory only, and requires the invited existing account's credentials. It checks the current actor's local pending request and known shifts before allowing submission. `sign_out_first` gives explicit instructions without automatically signing anyone out. No new-account, email delivery or password recovery capability is claimed.
- `AccountSettings({disabled})` changes only the authenticated account's password with current-password verification. It uses the shared 12–72-character/72-UTF8-byte policy and different-password requirement. Passwords are never put in the staff journal. Confirmed change requires sign-in again; `password_changed_sign_out_pending` explicitly means the new password applies even though session sign-out was not confirmed.

Staff commands are persisted before dispatch under an actor/branch key, retaining the original device in the frozen command and retried with their original ID/body. Access-link tokens and passwords are absent from those records. Matching ACKs clear the request before refresh; a subsequent refresh failure remains an acknowledged save, not a retry of the write. Raw application setup URLs appear only in the result panel after validation of their exact same-origin `/staff/accept#token=…` shape. Copying is manual and is never described as email delivery. Unknown/uncertain outcomes keep editing paused. Open-shift failures retain the command for retry after closing shifts. Only exact `staff_conflict`/409 and `invalid_staff_request`/422 responses clear a rejected command; the screen reloads authoritative staff access before editing resumes. Failed journal removal or refresh keeps editing paused. Other conflicts, limits, authentication failures and uncertain outcomes remain pending.

Tests: `pnpm exec vitest run tests/unit/pos/staff-ui.test.tsx`. The tests use synthetic accounts/password strings and mocked API/storage boundaries; they do not establish actual authentication-provider behavior, email delivery, production permissions or physical counter continuity. Design/future email flows: `docs/design/2026-10-16-staff-access-design.md`.

`PendingAccessRecovery()` checks the current session and that actor’s existing IndexedDB financial request when bootstrap is unavailable. It sends only the original body to recovery, validates matching cancellation/command/invoice/credit-note acknowledgements and document identity, and clears the local journal only after confirmation. Inactive unsaved requests remain pending until a manager restores access. It never dispatches a new sale, enrolls a counter or logs anyone out.

A restored manager on a newly enrolled counter can find the original branch request and use **Check saved change** after explicitly agreeing to cancel it if unsaved. This calls only staff recovery with the immutable original endpoint/body. A matching committed ACK is validated normally; only a matching durable cancellation clears an unsaved request. Another actor’s journal is not visible.
