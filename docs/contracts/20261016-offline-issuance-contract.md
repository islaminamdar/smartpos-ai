# Native offline issuance protocol v1

Status: implementation contract, 2026-10-16. This document does not enable live offline sales. Server grant allocation, historical reconciliation, native integration and acceptance remain release gates. Browser training records must never be imported as live invoices.

Implemented boundaries: the native calculator and strict signed-payload reader have shared financial/signature fixtures with TypeScript. `lib/pos/offline/validation.ts` independently recomputes historical financial fields and provides a pure import decision for exact retries, conflicting identity, device-chain order and cumulative grant budgets. The server service and candidate migration017 now implement enrollment, reservation, signed bundle attachment, actual historical financial import, durable acknowledgements and terminal declarations per authority. These are disabled by default and are not a released native checkout. Native grant/schema validation and the internal atomic intent/receipt engine are now implemented and tested with synthetic Android records; production local unlock, native time/enrollment handoff, counter integration, reporting and acceptance remain release gates.

## Server API and private configuration

`POST /api/pos/offline/enroll` and `/authority` require the current staff session, the expected website Origin, enabled online/live gates and `POS_OFFLINE_ISSUANCE_ENABLED=true`. SQL additionally requires an explicitly enabled branch policy; migration017 enables no existing branch. Enrollment requires a current manager/owner and a signed proof from the proposed P-256 key, bound to actor, branch, existing device and request. SQL checks five-minute freshness only on first enrollment, so exact response recovery still works after that window. A device key cannot be silently replaced or used by two devices.

The authority request chooses a bounded count, lifetime (60–86,400 seconds), invoice/gross limits and cash/recorded-card/mixed permissions, all constrained by private branch policy. Its request ID is the immutable authority ID. Reservation records an immutable snapshot and unsigned authority before signing; the attach RPC binds exact canonical payload hashes and caches the first complete signed envelopes. Signing failures leave an explicit recoverable reservation; they never cause automatic number reuse. A new grant requires the previous authority to be sealed, and the device chain continues across grants.

`POST /api/pos/offline/import` and `/seal` authenticate the historical device signature. They intentionally do not depend on current staff login, branch/device active status or new-sale flags. The exact routes remain reachable when online selling is paused. They use the trusted inbound-proxy source key and a private SQL rate budget of 600 requests/minute/source; this does not consume the login budget. Bodies are bounded while streaming. Clients retain queued evidence on 429/503 and must not collect payment again.

Private server configuration: `POS_OFFLINE_SIGNING_KEY_ID` selects an entry in `POS_OFFLINE_SERVER_KEYS`, a JSON array of `{id,publicKeySpki,privateKeyPkcs8?}` with canonical base64url DER SPKI and PKCS8. Only the active signer needs a private key. Keep historical public keys through rotation; never put private keys in the repository, app or client environment. The service verifies the signing key pair before allocating numbers. The candidate native host now uses bundled trust anchors and challenge-bound signed preparation handoffs; matching production key configuration and release acceptance remain pending. Incoming envelopes cannot supply their own trusted server key.

All `pos_offline_*` public RPC entry points are service-role-only, with helper/table access further restricted. The service verifies device signatures and historical schemas/calculations; SQL independently checks scope, arithmetic, ownership, chain, budgets and unique identities under transaction locks. It atomically inserts original orders/lines/payments/documents, private provenance and the first signed ACK. The kitchen trigger checks that private provenance before projecting a document, preventing delayed preparation on reconnect. Import does not regenerate documents from the current menu/profile.

Invalid signatures never quarantine a device. A device-authenticated financial anomaly is retained as an immutable reconciliation exception and blocks renewal/shift closure. Repeated identical evidence returns the original exception ID. A normal missing-predecessor exception gets a separate append-only resolution when that exact receipt is later committed; unrelated calculation, collision or budget exceptions remain unresolved. An operator resolution workflow is still required before customer activation. Shift closure requires a sealed authority with the complete declared chain and no unresolved exceptions; expiry alone does not close it.

ACK payload: `{kind:'offline-ack',schemaVersion:1,id,issuanceId,payloadSha256,authorityId,keyEpoch,deviceSequence,receivedAt}` signed by a configured server key. An exact retry returns the first ACK, even after later imports. Seal payload: `{kind:'offline-seal',schemaVersion:1,id,authorityId,keyEpoch,deviceId,finalSequence,finalEventSha256}` signed by the device. A seal is terminal for that authority, not the key epoch; the native app must durably stop issuance from it before sending the declaration. The seal response currently relies on HTTPS and is not a standalone signed custody ACK.

Verification commands: `node tests/integration/pos-offline.mjs /path/to/pglite/dist/index.js` checks disposable SQL behavior; `OFFLINE_TEST_PGLITE_ENTRY=/path/to/pglite/dist/index.js npx vitest run --config vitest.offline.config.ts` runs real P-256 signatures through the production service and a disposable SQL engine. Neither command connects to production. Independent PostgreSQL session/concurrency checks are an additional gate, not replaced by the embedded tests.

## Wire signature and canonical bytes

`SignedEnvelope = {format:'pos-signed-v1', alg:'ECDSA-P256-SHA256-DER', keyId:string, payloadBase64Url:string, signatureBase64Url:string}`. No extra properties. Base64url is unpadded and canonical. Payload is UTF-8 JSON with recursively sorted object keys, arrays in original order, integer safe numbers only, no undefined/nonfinite values or lone UTF-16 surrogates; no Unicode normalization. Signed bytes are exactly decoded payload bytes, not a reconstructed subset. This is a private envelope format, not JWS. Maximum decoded payload 1 MiB; keyId 1–120 ASCII letters/digits/dot/underscore/hyphen.

P-256 with SHA-256; signature is strict ASN.1 DER sequence of positive minimal integers r and s, each in the P-256 scalar range. DER length is variable (up to 72 bytes); do not incorrectly reject valid shorter integer encodings. Node uses `dsaEncoding:'der'`, Android `SHA256withECDSA` directly. WebCrypto needs DER-to-P1363 conversion. Fingerprint is lower-case SHA-256 of DER SubjectPublicKeyInfo, not JSON serialization of a JWK. A device issuance envelope keyId must equal its enrolled SPKI fingerprint. Trusted server keys are configured independently of the received envelope. Never trust a public key embedded in its own signed message.

Idempotency and chain hashes cover canonical payload bytes, not signature bytes: valid ECDSA signatures can differ for the same payload. Retain the first complete accepted envelope for evidence, but do not treat a different valid signature over identical authenticated payload as a new sale.

## Exact payloads

Authoritative TypeScript schemas: `lib/pos/offline/contracts.ts`. UUIDs and SHA-256 hex values use lower case; timestamps are UTC ISO strings with millisecond precision.

Snapshot: `{kind:'offline-snapshot',schemaVersion:1,id,organizationId,branchId,createdAt,profile,products,calculationVersion:'offline-line-v1',offers:[]}`. Profile is the existing immutable MerchantProfile. Product: `{id,name,category,unit:'piece'|'pack'|'kg',unitPriceFils,taxRateBps,revision}`; only authorized available products are included. Maximum 2,000 unique products. Media is a separate nonfinancial cache. Scope must match profile. Snapshot SHA-256 is over canonical payload bytes. No real merchant values are bundled in the APK/public training assets.

Authority: `{kind:'offline-authority',schemaVersion:1,id,organizationId,branchId,deviceId,actorId,deviceKeySha256,keyEpoch,shiftId,snapshotId,snapshotSha256,issuedAt,notBefore,expiresAt,invoiceRange:{prefix,first,last},maxInvoiceTotalFils,maxGrossFils,permissions:{cash,recordedCard,mixedTender},policy:{refunds:'online-only',sharedTabs:'online-only',offers:'online-only'}}`. `keyEpoch` is a UUID. Prefix matches existing fiscal prefix `[A-Z0-9]{2,16}`. Integer range 1..9,999,999,999, no more than 1,000 numbers per authority. Validity at most 24 hours is a protocol ceiling, not the configured operational default. Max invoice 100,000,000 fils; total grant budget no greater than its count times invoice limit. Authority is tied to an online-opened device-owned shift for the first slice; no shared drawer ownership.

Issuance: `{kind:'offline-sale',schemaVersion:1,id,authorityId,authoritySha256,snapshotSha256,deviceSequence,previousEventSha256,document,clock:{estimatedServerAt,bootId,elapsedRealtimeMs},paymentIntentId}`. `id` equals `document.orderId`; `document` is an existing schemaVersion1 tax invoice (maximum 200 lines). The native engine computes its complete immutable lines/totals/tenders from the snapshot; UI totals are advisory. No caller-defined unit price, tax, merchant identity or document number is trusted. `document.issuedAt` equals estimatedServerAt. First device event has previousEventSha256=null; later records chain the canonical previous issuance payload hash. Sequence is positive, monotonic for the key epoch, and checked against persisted device state. The device signs the exact canonical issuance using the enrolled key. Signature is stored with the immutable receipt and outbox.

## Native ledger boundary

Before payment collection, persist a unique payment intent with actor/device/shift/authority/cart hash and the presented amount. Cashier confirms externally processed card success; application never retries a card charge. An intent without committed issuance after restart is an uncertain payment requiring human reconciliation, not a fresh charge instruction.

After confirmation, one native SQLite transaction checks local unlock, signed authority/snapshot identity and time, remaining budget and next number; calculates price/tax; allocates number; signs payload; inserts immutable receipt, ledger chain state and outbox; marks intent committed. Publish success only after commit. A retry of the same intent returns the identical issuance; changed input conflicts. Full disk, signature failure, invalid authority or failed commit produces no success receipt. SQLite storage and signing keys stay outside browser IndexedDB and JavaScript credentials. Typed native methods only; bundled app origin only; no remote privileged WebView content or arbitrary SQL bridge.

The internal native engine implements these operations behind a package-private construction boundary; sale issuance is not exported by the current preparation/recovery plugin. SQLite version2 adds immutable bundles/intent context/cancellations, monotonic authority usage and a device-epoch chain. Only one uncertain intent is allowed; explicit no-payment cancellation is retained separately. Existing receipts, ACKs and device identity survive the additive upgrade. Exact committed intent replay precedes new-sale clock/unlock checks; valid server ACKs remove only their matching upload entry. Native test output is independently verified by the TypeScript historical validator.

Minimum bridge methods: installVerifiedBundle(snapshotEnvelope,authorityEnvelope); getState(); beginPaymentIntent(intentId,input); commitPaymentIntent(intentId); getReceipt(orderId); listPendingIssuances(); acknowledgeIssuance(exactServerAck). Checkout input is frozen by the internal engine as authorityId, serviceType, customer, productId/quantityMilli lines, cashTenderedFils, recordedCardFils and presentedTotalFils. Explicit confirmation commits that exact prepared tender; changing it requires resolving the earlier intent. The sale write bridge and its authenticated caller flow still require review before exposure. Historical upload and explicit PIN-confirmed allocation finishing are connected separately; see `apps/android-pos/RECONCILIATION.md`. SQLite version3 adds immutable upload exceptions and operational seal confirmations without altering original custody. Receipt, identity, counter and outbox must never be restored through ordinary app backup into a second active issuer. Disable automatic device-to-device/app backup for those files; archive recovery is read-only until online controlled key-epoch rotation and allocation reconciliation.

## Server allocation and reconciliation requirements

New dedicated endpoints/RPCs are required. Do not send an issued invoice to `/api/pos/sync`: that online writer deliberately revalidates current menu/profile/access/shift state and allocates a new server number/time. Reserve disjoint blocks atomically from existing branch invoice counter, record every reservation, never recycle unused numbers. Concurrent online invoices start after the reservation. Future legal/accounting review must approve documented number gaps/order before production activation.

Grant minting uses current actor authority15 then device/shift/profile locks in existing financial order, captures immutable complete catalogue in a consistent transaction, and reserves numbers/quota. Signing delivery retries return the same grant. Lost signing response cannot allocate a fresh block silently. Signed grants have explicit lifetime and spend limits; revocation immediately stops renewal but cannot instantly reach disconnected devices.

Import verifies device signature and stored historical grant/snapshot, exact receipt calculation, number ownership, sequence/hash chain, per-grant spend and identity; it must NOT reprice from current products, regenerate receipt, require current membership, reject merely because the grant has expired at upload time, or silently delete/void an already-issued bill. A narrowly scoped device-authenticated upload channel accepts historical evidence after staff access removal without permitting reads/new grants. Exact same issuance returns original acknowledgement; mismatched request/number/hash is retained as a reconciliation exception and blocks further grants. Anomalies are durable, never an instruction to collect again. Server independently recomputes every financial field against historical immutable data before ordinary ledger import.

Import must atomically create orders/lines/payments/documents and provenance, preserve original issue time, distinguish receivedAt, reconcile device shifts and update grant usage. Existing reports need per-device missing-sequence/last-upload/incomplete labels. Already issued records remain uploadable even when new sales are paused. Server close must await the complete declared local chain; device-authorized offline close/cash movements are a later contract, not implemented by this v1.

SQL016 `pos_project_kitchen_document` currently queues new invoices. Imported offline bills need private trusted provenance to prevent delayed duplicate preparation. Never claim cloud kitchen delivery while offline; first slice uses device-owned orders and explicit local/manual kitchen handling. Cloud shared tables cannot be settled offline without an exclusive ownership protocol.

## Time, permissions and offers

Native time anchors server time to elapsedRealtime within a boot, persists observed wall-clock high water and boot identity, checks drift, and fails closed on detected rollback/anomaly. Reboot alone must not require connectivity; recover conservatively from persisted wall-clock evidence within grant bounds. Android does not provide this app a general tamper-proof cross-reboot offline clock: a compromised clock/device can defeat time assumptions. Signatures authenticate authority and records, not physical payment or trustworthy creation time. Budget/count bounds and managed-device policy limit exposure. Local enrolled staff unlock is native and rate limited, not a cached server password or an arbitrary manager PIN conferring authority. Root must define and test local unlock implementation before real activation.

First slice has signed empty offers and explicit online-only offer policy. Later all four existing offer types reuse frozen definitions/calculation version. Global coupon/usage limits require disjoint device redemption reservations deducted from online available quota before offline use; unused reservations cannot be reused while a device may still spend them. Scheduled offers depend on the stated clock trust. Per-customer limits remain unsupported without verified identity. Offline refunds require original-sale exclusive refund authority to avoid independent cash refunds across devices; until then refunds remain online.

## Acceptance slice

Two separately enrolled Android instances obtain distinct grants, disconnect, independently issue piece/pack/weighted cash/recorded-card/mixed sales, survive force-stop and reboot, reopen identical receipts, and reconnect after menu/profile/access changes. Verify exact original imports, retry after lost ACK, number collision attempts, full-storage rollback, expired grants, clock changes, replacement/reinstall, failed signing, no duplicate kitchen queue and honest incomplete reports. Test against synthetic server fixtures before approved merchant activation. No APK or protocol-only test can by itself certify live offline readiness.
