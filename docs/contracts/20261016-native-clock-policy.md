# Native offline clock policy

Status: candidate native algorithm, 2026-10-16. This does not enable offline selling or provide a tamper-proof clock. The internal checkout engine persists anomalies and accepted time observations. Android OS clock and boot readings, fresh trusted server-time handoff and local staff unlock still require production integration before customer use.

`OfflineClock` accepts native `Reading(bootId, elapsedRealtimeMs, wallTimeMs)` values. The boot ID must remain stable for the entire boot and change after a reboot. WebView input must never supply these values. Installation uses `anchor(freshTrustedServerMs, reading)` only after a fresh authenticated native HTTPS exchange. An old signed authority's issue time is not a fresh time observation. Exact bundle installation retries must preserve the existing clock state and counters.

Within a boot, estimated server time advances using elapsed realtime from the original anchor. Every successful observation records the latest elapsed realtime and wall/server high-water marks. Any observed wall-clock rollback or elapsed-realtime rollback fails closed. The difference between wall-clock progression and elapsed-realtime progression may not exceed 120 seconds. This tolerance compares with the original boot anchor, so repeatedly advancing the wall clock in small steps cannot reset the allowance.

Across a reboot, the estimator adds the larger of wall time since the previous persisted observation and the current boot's known elapsed realtime to the previous server high-water mark. It then establishes a new monotonic anchor. Wall-clock rollback still fails closed; a new boot's elapsed time more than 120 seconds beyond the wall interval is inconsistent and rejected. This supports offline reboot recovery while conservatively accounting for known uptime. It cannot prove how long a powered-off or compromised device was inactive. A coordinated clock/state rollback on a compromised device is outside this estimator's guarantees.

Authority start time is inclusive and expiry is exclusive. `clock_expired` and `clock_not_started` are authority bounds, not permanent clock anomalies. `ClockException.isAnomaly()` distinguishes these from `clock_rollback`, `clock_drift` and `clock_invalid_state`. The caller must latch anomalies durably even when the attempted checkout transaction is rejected. A process restart or retry must not clear the latch. Controlled online recovery requires a separate reviewed workflow; this class does not clear a blocked authority.

`Tick.nextState` must be persisted atomically with each accepted payment-intent preparation or receipt commit. `State.toJson()` and `State.fromJson()` use strict canonical JSON, reject unknown/missing/coerced values and check cross-field consistency. Clock state is immutable in memory. Receipt retries return the original committed record before requesting new clock authorization; expiration must not hide previously issued bills.

Verification: 14 isolated Java/JUnit tests cover monotonic progression, accumulated drift, rollback, process-state round trips, conservative synthetic reboot, exact expiry, malformed persistence and overflow. Three Android instrumentation tests exercise Android JSON/runtime compatibility with synthetic readings; their execution is tracked separately. These tests do not constitute physical reboot, hardware clock-tampering or full checkout acceptance.
