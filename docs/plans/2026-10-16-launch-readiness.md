## Manager payment-review UX plan

This is the next proposed workflow, grounded in [the resolution contract](../contracts/20261016-offline-payment-resolution.md), not a description of an implemented screen. It handles **unissued** native intents. An existing invoice follows the ordinary invoice/credit workflow after reconciliation; it must not be reclassified as an unissued payment.

### Entry and state vocabulary

Add a manager-only **Payment reviews** view scoped to the selected branch. Show a complete active count with a paged list, oldest unresolved first, then read-only history. Each row shows counter, cashier, original payment time, planned net amount/tender, age and a plain-text status. Unknown totals are unavailable, never zero. No public lookup by reference. Phone rows stack at 320/375px; desktop provides a readable detail panel. Primary actions at least 48px; no colour-only warnings.

| State | Cashier wording | Manager action |
|---|---|---|
| Local freeze only | Saved on this device · not sent. Do not collect again. | No server case exists yet; a reference is not proof of submission. |
| Registration uncertain | Checking saved review request | Read/retry the same freeze evidence. Do not create replacement request/payment. |
| Registered, no decision | Waiting for manager review | Inspect exact basket, scope and payment evidence; keep pending if uncertain. |
| Conflict or original invoice found | Payment needs investigation | Preserve evidence and show canonical original invoice if matched. Disable return/void through this flow. |
| Decision saved, signature/delivery pending | Manager decision saved · device confirmation pending | Recover the existing result; never offer a second external refund. |
| Native verified/stored outcome | Payment returned / Card authorization void recorded | Show separate payment acknowledgement, original reference and delivery status. No tax credit note is invented. |

The manager detail shows original branch/counter/cashier/shift, intent time, expiry/block reason, immutable lines and planned tender/change, exact freeze reference, recorded conflicts and decision/delivery status. Keep signature/hash detail collapsed for support. These amounts describe the plan until attested; they do not prove collection. A local freeze cannot appear in an online list before successful registration.

### Decision choices and exact evidence

1. **Keep pending / payment status uncertain.** Preserve custody and investigation notes; it is not a terminal resolution or an escape from the hold. If note persistence is not implemented, do not show a successful “note saved.”
2. **Record full funds returned.** Available for the complete planned cash/card legs only after the manager confirms money was actually collected and fully returned externally. Display each leg separately, original open drawer for cash, observation/completion times, method, reference and reason. A settled-card refund belongs here, not card authorization void. Mixed cash/card is permitted only when both legs are fully returned; mixed return/void, partial amounts, different drawer, missing change or uncertain provider results stay pending.
3. **Record card authorization void.** Card-only, before settlement, exact full planned card amount with terminal/provider reference and authorization-observed/void-completed times. Copy says the app records an already completed void; it does not perform it. No automatic retry of terminal activity.

Use a review step followed by fresh server-authenticated manager confirmation and a checkbox bound to case ID, freeze hash, full evidence and outcome. Re-read current case and role before enabling the final action. The button names the record being saved, not “Refund now.” Do not request PAN, CVV, passwords or unnecessary customer information. Editing any amount/evidence/outcome clears consent. Stale reads retain visible information with actions disabled. Lost response freezes the exact request and changes the action to **Check saved decision**.

Accounting boundary: the unissued intent has no booked sale/revenue. Same-drawer full collection and equal return are paired evidence with zero net drawer effect; do not manufacture `refund.full`, a negative invoice or a standalone cash withdrawal. Example: planned AED 100 cash tender, AED 80 total and AED 20 change means AED 80 net return. If actual change/retained funds differ, leave unresolved. No generic “resolved” switch and no silent native unfreeze.

### Completion and blocked cases

Server decision, signature attachment and device acknowledgement are separate indicators. Recovery may attach/retrieve the existing signature after a response failure; it never repeats the physical return or decision. Native clears custody only after validating and durably saving the exact signed outcome. Receiving a decision does not renew expired permission, open another allocation or close a cash shift. Retained funds/current-time invoice is a separately gated phase requiring the owner/accountant decision; the UI must not force a return or backdate an invoice when that option is unavailable.

Business choices before enabling: manager/owner amount ceiling or second approval; required evidence/retention; original-drawer-only/full-tender policy; approved tax/accounting treatment for retained funds; original cashier/device-loss recovery. Default engineering behavior remains blocked/pending where these are unresolved. This plan does not authorize external payment actions.

### Acceptance that proves the workflow

Test and inspect real server/native round trips with synthetic funds: cash full return, settled-card return, card authorization void, full mixed return; wrong drawer/partial/unknown settlement rejected; matching invoice/conflicting import preserved; two managers racing; revoked manager; freeze-versus-import/online invoice; signature failure after saved decision; lost response; offline/locked/revoked device retrieval; restart at each boundary; no duplicate payment/kitchen ticket; no unintended shift/authority reopening. Review 320/375/1280px and keyboard/focus behavior. Then obtain physical-device and supervised manager acceptance. Unit tests alone cannot establish an actual card void, returned cash or delivery to the device.

## Delivery order after custody foundation

The required manager resolution/receipt custody foundation comes first because the requested offline sales cannot safely launch with an unresolvable collected payment. Once that path and controlled next-allocation/recovery are usable, complete native/server two-device acceptance, actual POS printing, signed update preservation and manager handover before enabling production offline issuance.

Highest-value missing web increments, based on the restaurant/branches scope:

1. **Branch operations and exception dashboard:** all open shifts, unresolved requests/payments, unpaid orders, kitchen notices, last successful data read, and close/handover checklist. Build authoritative aggregates; never synthesize healthy/zero states. This gives the owner a practical daily control screen and makes custody issues visible.
2. **Partial item/weight returns:** exact original line/discount/VAT allocation, cumulative quantity/tender caps, manager reason/approval and immutable credit evidence. Test concurrent returns, offer interaction and kitchen consequences before cashier use.
3. **Inventory baseline:** unit-aware opening counts, receipts, waste and adjustments first; recipe consumption and transfers follow. Do not start with a dashboard claiming ingredient precision without a ledger. This addresses sweets/restaurant waste and branch control more directly than another cosmetic analytics chart.
4. **Menu administration finishing:** authentic photo upload, variants/modifiers and controlled branch overrides with source/revision review. Add kitchen modifier snapshots, not free-text promises unsupported by checkout.
5. **Kitchen courses and station routing:** explicit hold/fire/course transitions, station item routing and stop/change acknowledgement, integrated with existing stable dispatch identity. Couple with selected printer/display hardware acceptance.
6. **Customer profiles and loyalty ledger:** optional consent-based identity, earned/redeemed points with duplicate protection and return reversal; balances/history before tiers/marketing. Keep guest checkout fast.
7. **Cross-branch owner reports and commercial onboarding:** explicit incomplete/offline labels, branch permissions and comparable periods; complete staff-email delivery and branch setup. Complete PayPal sandbox/live commissioning in parallel with authorized merchant configuration, not by simulated provider success.

Delivery connectors, QR ordering, advanced forecasts and Windows packaging follow these operational priorities. This ordering is a proposed value/risk sequence, not a reduction of the agreed all-features goal or an added paid tier.
